# The /brain Page

The `/brain` page is BosskuAI's observability dashboard for the AI's internal state. It gives you a live view into what the system has learned, what it remembers, which skills are being generated, and whether the self-learning loop is healthy.

## The 7 Tabs

### 1. Overview

A summary dashboard showing:

- **Learning velocity** — how many patterns were extracted this week vs. last week
- **Active skills** — count of currently active skills with average quality score
- **Memory health** — total memories, stale count, conflict count
- **Pending reviews** — skill candidates awaiting approval, feedback events awaiting triage
- **Last brain run** — timestamp and status of the last `LearningEngine` job
- **Soul version** — currently active soul version

Use the Overview to get a quick sense of whether the system is learning from recent runs or stagnating.

### 2. Memory Streams

A time-ordered feed of all memory entries, grouped by tag. Each entry shows:

- The memory content
- Confidence score with a visual meter
- Staleness indicator (green = fresh, yellow = stale, red = very stale / conflicted)
- Source run link
- Last confirmed timestamp

You can filter by tag, confidence range, and date. Click any memory to see its full detail, including which runs cited it and whether it has active conflicts.

Use Memory Streams to audit what the AI "knows" about your project before it goes wrong in a run.

### 3. Learning Inbox

All unreviewed learning events generated by `FeedbackLearningService`. Each event shows:

- The original user feedback (text, thumbs up/down, or rating)
- The run it was attached to
- The pattern it was matched to
- The suggested action (reinforce the pattern, flag for skill improvement, or add anti-pattern)

Events stay in the inbox until explicitly acknowledged. Acknowledging an event confirms the learning was valid. Rejecting it marks the feedback as noise and prevents it from influencing the skill candidate pipeline.

### 4. Skill Candidates

All auto-generated skill drafts awaiting approval. Each candidate shows:

- Draft skill name and description
- Full generated SKILL.md content (editable inline)
- The pattern that triggered generation (with occurrence count and contributing run links)
- `requires_manual_review` flag for risky categories
- Quality score estimate based on the draft

Actions: **Approve**, **Edit then Approve**, **Reject with reason**.

See [`auto-skill-generation.md`](auto-skill-generation.md) for full approval workflow details.

### 5. Feedback Learnings

A historical view of all feedback that has been processed (acknowledged or rejected), showing:

- Which patterns were reinforced by positive feedback
- Which skills were flagged for improvement by negative feedback
- Trend: is user satisfaction improving over time?

This tab is useful for quarterly reviews — if a pattern keeps receiving negative feedback even after skill improvements, the approach needs a more fundamental rethink.

### 6. Brain Health

A health check report that runs on demand (or on a schedule). It checks:

- **Skill quality distribution** — histogram of quality scores across all active skills; a large cluster below 0.5 indicates a skill library that needs pruning
- **Pattern coverage** — what percentage of recent runs matched a specific skill vs. fell back to the `cofounder` catch-all; high fallback rate means there are under-served task types
- **Memory freshness** — percentage of memories above 0.6 confidence; a declining trend suggests either rapid project change or the confirmation loop is broken
- **Learning engine latency** — average time from run completion to pattern extraction; high latency means the background job queue is backed up
- **Conflict ratio** — unresolved conflicts as a percentage of total memories; above 5% warrants a conflict review session

Each health check item has a status (OK, Warning, Critical) and a suggested action.

### 7. Conflicts

All unresolved memory conflicts detected by `MemoryConflictDetector`. Each conflict shows:

- The two (or more) conflicting memory entries side by side
- The reason the detector flagged them as contradictory
- Links to the source runs for both entries

To resolve: click the winning memory and confirm. The loser is archived and the winner's confidence is restored to `0.9`.

Unresolved conflicts do not block runs, but they cause the orchestrator to inject both conflicting facts with a `[conflict]` annotation, which can confuse the model. Resolve conflicts regularly to maintain run quality.

## Practical Workflow

1. **After a significant project milestone**: open Brain Health and check skill coverage and memory freshness
2. **Weekly**: clear the Learning Inbox, review Skill Candidates, resolve any Conflicts
3. **When a run produces unexpected output**: check Memory Streams to see what context was injected, and Feedback Learnings to see if a previous bad pattern is still influencing results
4. **Before approving a new skill candidate**: click through to the contributing runs to verify the pattern is real and the draft approach is sound
