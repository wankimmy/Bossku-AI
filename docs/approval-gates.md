# Approval Gates

Approval gates are hard stops in the execution pipeline that require a human decision before a step proceeds. They exist because some operations are irreversible, have wide blast radius, or carry security implications that no AI should execute autonomously.

## Operations That Always Require Approval

The following step types always trigger an approval gate, regardless of skill, context, or user history:

| Operation | Why |
|---|---|
| `terminal_command` with risk level `high` or `critical` | Shell commands can cause irreversible system changes |
| `external_http` | Outbound HTTP calls can trigger real-world side effects (webhooks, third-party APIs) |
| `env_mod` | Modifying `.env` or environment variables affects all running processes |
| `deployment` | Any production or staging deployment |
| `secret_rotation` | Rotating API keys, tokens, or passwords — getting this wrong causes outages |
| `high_cost` | Any step estimated to cost more than the configured `high_cost_threshold_usd` |

These are the default gates. You can add additional triggers via the governance rule editor (see [`governance.md`](governance.md)).

## How ApprovalGateService Works

`ApprovalGateService` is called by `ExecutorService` before each step. It:

1. Receives the step object including its `type`, `content`, and `risk_level` from `RiskClassifier`
2. Checks whether any gate condition applies
3. If a gate applies:
   a. Saves the step with status `pending_approval`
   b. Creates an entry in the `approval_requests` table
   c. Emits an `approval_pending` SSE event so the UI immediately shows the approval prompt
   d. Blocks execution — the executor pauses and polls for the approval decision
4. If no gate applies, execution continues immediately

The executor waits up to `APPROVAL_TIMEOUT_SECONDS` (default: 300) for a decision. If no decision is made in that window, the run times out with a `approval_timeout` error. The run can be resumed later by approving the pending request via the API.

## Approving via the UI

When a run hits an approval gate, the run detail page at `/runs/{id}` displays:

- The step that is waiting
- The full step content (the command, URL, or env key to be changed)
- The risk level and the rule(s) that triggered the gate
- An **Approve** button and a **Reject** button
- An optional **Edit** field to modify the step content before approving (e.g. to fix a risky command)

Clicking **Approve** resumes execution immediately. Clicking **Reject** marks the step as `rejected`, stops the run, and records the rejection reason in the audit trail.

## Approving via the API

For automated or CI/CD workflows, approvals can be submitted programmatically:

```http
POST /api/approval-requests/{id}/approve
Authorization: Bearer <token>
Content-Type: application/json

{
  "approved_by": "ci-bot",
  "note": "Approved by automated pipeline check"
}
```

```http
POST /api/approval-requests/{id}/reject
Authorization: Bearer <token>
Content-Type: application/json

{
  "rejected_by": "ci-bot",
  "reason": "Deployment not permitted outside release window"
}
```

Only users with the `approve_runs` permission can approve or reject. Configure this permission in `/settings/users`.

## Listing Pending Approvals

```http
GET /api/approval-requests?status=pending
```

Returns all runs currently blocked on an approval gate. The `/runs` list page also shows a badge count of pending approvals at the top. Admin users receive an in-app notification when a new approval gate is triggered.

## Disabling Gates for Specific Skills (Advanced)

Some skills in automated workflows need to operate without approval gates (e.g. a skill that runs automated test suites via terminal commands). You can mark a skill as `trusted_execution` in the skill editor. With this flag:

- `terminal_command` steps generated by this skill bypass the `high` risk gate (they still require approval at `critical`)
- The skill must have `quality_score >= 0.8` and `trusted_execution` requires an admin to explicitly grant

This is a deliberate friction point. Automation that bypasses human oversight should be earned, not defaulted.

## Audit Trail

Every approval decision is recorded in `approval_events`:

- Step ID and run ID
- Decision (approved/rejected)
- Who decided and when
- The step content at time of decision (immutable snapshot)
- Whether the content was edited before approval

This audit trail supports compliance requirements (SOC 2, ISO 27001) that demand evidence of human oversight over automated systems.
